## Temuan

### APP-01 — Tinggi / privasi: email dan catatan pelapor dikirim ke pembaca umum

Lokasi: `server/index.js:399–427`, khususnya `ownerEmail` dan
`submission.reports` pada respons `GET /api/library`.

Reproduksi terisolasi:

1. Buat akun pemilik, pelapor, pembaca lain, dan admin.
2. Pemilik mengirim Sharing dan admin menyetujuinya.
3. Pelapor mengirim alasan `other` dan catatan laporan.
4. Pembaca lain, bukan admin/pelapor/pemilik, memanggil `/api/library`.
5. Respons memuat email pemilik serta seluruh objek laporan:

```json
{
  "ownerEmail": "owner@qa.example.test",
  "submission": {
    "reports": [
      {
        "by": "reporter@qa.example.test",
        "reason": "other",
        "note": "QA confidential report note"
      }
    ]
  }
}
```

Dampak: meskipun antarmuka hanya memerlukan jumlah laporan/penanda laporan,
semua pembaca yang login dapat membaca identitas dan isi catatan pelapor lewat
respons jaringan. Ini bukan kebocoran password atau akses admin, tetapi cakupan
data publik internal terlalu luas. Tidak diasumsikan ada janji anonimitas pada UI.

Rekomendasi:

- Endpoint Perpustakaan hanya mengirim nama penulis, identitas publik konten,
  jumlah laporan, serta penanda `isOwn`/`hasReported` yang diperlukan UI.
- Jangan mengirim email pelapor atau catatan laporan ke pembaca umum.
- Gunakan identitas publik/non-email untuk pengaitan konten dan pemeriksaan
  kepemilikan di frontend. Jangan hanya menghapus email dari tampilan.
- Batasi detail laporan pada akses yang memang memerlukannya, terutama admin.
- Tambahkan tes bahwa pembaca biasa tidak menerima `by`, catatan laporan, atau
  email pemilik dari respons Perpustakaan.

Status: **diperbaiki; tes privasi, workflow admin, dan browser lulus**.

### APP-02 — Sedang / responsif: kontrol demo membuat halaman Pohon melebar

Lokasi: `src/styles.css:754–782,1273` — `.tree-care-row` dan tombol demo.

Reproduksi:

1. Login sebagai user pada konfigurasi `ALLOW_DEMO_TOOLS=true`.
2. Buka halaman Pohon dengan viewport 900 × 700 px.
3. Browser Windows menampilkan scrollbar vertikal sehingga lebar konten efektif
   `document.documentElement.clientWidth` adalah 885 px.
4. Lebar dokumen `scrollWidth` menjadi 899 px dan muncul scrollbar horizontal.
5. Tombol `#healthyButton` memiliki sisi kanan sekitar 899,36 px, melewati batas
   konten efektif.

Penyebab: kontrol perawatan/demo tidak menyusut dan barisnya baru di-wrap pada
breakpoint sempit. Lebar tablet tertentu tidak cukup untuk seluruh tombol.
Elemen awan juga melewati viewport secara dekoratif, tetapi berada dalam scene
yang di-clip; tombol Sehat adalah elemen interaktif yang melewati batas halaman.

Pemeriksaan geometri sebelumnya yang hanya membandingkan `scrollWidth` dengan
`innerWidth` dapat melewatkan masalah ini: 899 masih lebih kecil dari 900,
tetapi lebih besar dari lebar konten efektif 885.

Rekomendasi:

- Izinkan `.tree-care-row` melakukan wrap pada lebar tablet juga, bukan hanya
  ≤680 px; sesuaikan ukuran panel informasi decay agar tombol tetap masuk.
- Pertahankan semua tombol yang diminta pengguna, bukan menyembunyikan Boost.
- Tes ulang dengan `scrollWidth <= clientWidth + 1`, pada demo aktif/nonaktif
  serta viewport di sekitar 900 px.

Status: **diperbaiki; 72 kombinasi geometri tanpa overflow**.

### APP-03 — Keterbatasan fitur yang masih ada: file video belum dibagikan lintas akun

Reproduksi: user mengirim video tanpa URL tetapi dengan metadata attachment.
Server menerima, admin dapat ACC, dan pembaca lain menerima metadata nama,
ukuran, MIME type, tetapi URL materi tetap kosong.

Video berada di penyimpanan browser pengunggah, bukan file yang diunggah ke
server/object storage. Tautan HTTP/HTTPS tersedia dan bekerja sebagai sumber
bersama. Ini keterbatasan yang sudah didokumentasikan, bukan regresi baru.

Rekomendasi: sediakan object storage dengan endpoint upload/download terkontrol,
atau wajibkan URL yang dapat diakses bersama saat publikasi konten video.

Status: **belum tersedia; gunakan tautan sebagai alternatif**.

## Alur yang berhasil diverifikasi

- Register/login/logout; cookie HTTPS HttpOnly/Secure/SameSite; sesi setelah
  logout ditolak; password salah dan email duplikat ditolak.
- Field role admin palsu pada register diabaikan; user tetap role user.
- API admin menolak user biasa; proteksi admin terakhir dan pergantian role.
- `PUT /api/state` ditolak; input URL berbahaya ditolak server.
- Idempotensi submit, compare-and-swap state, dua submit serentak tetap tersimpan.
- Learning dua pertanyaan: jawaban salah ditolak; semua jawaban benar + konfirmasi
  baca membuka penyelesaian; reward tersimpan di server dan tidak ganda.
- Bintang tanpa komentar tidak terkirim; draf ulasan bertahan saat refresh state;
  rating + komentar tersimpan dan memberi 1 Air.
- Ulasan tampil inline, nama dan penanda Anda terlihat, rata-rata 4,5 sesuai
  fixture, pilihan materi memuat ulasan yang sesuai. UI ulasan tidak menampilkan
  email pengguna.
- Sharing dengan URL tersimpan pending; laporan melalui menu titik-tiga;
  admin ACC dengan konfirmasi; pemilik tidak bisa melaporkan konten sendiri.
- CRUD modul dengan konfirmasi dan pembacaan ulang; penghapusan akun dummy.
- Boost Demo menambah 10 Air dan 6 Pupuk; Boost Level naik satu tingkat;
  Turun Level turun satu tingkat; Menguning/Mati/Sehat tersimpan;
  simulasi +7 hari tersimpan; penambahan 0,5 Pupuk bekerja;
  kontrol demo tetap aktif setelah reload.
- Saat flag demo tidak diberikan, kontrol disembunyikan dan tindakan demo
  ditolak backend. Saat flag aktif, user biasa dapat menggunakan kontrol sesuai
  permintaan pemilik prototype. Ini keputusan konfigurasi, bukan bypass role.
